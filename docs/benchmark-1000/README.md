# 1000 张测试表格：官方基线与 OCR 系统对比

2026-11-11 完成。同一批固定随机抽取的 1000 张 PubTables-1M test 图片，两套流程全部完成，均无运行失败。官方评价条件基线的结果接近论文，支持结构识别模型的推理与评估复现有效；当前 OCR 系统的文字识别与分配仍需改进。

## 核心结果

以下 GriTS 数值均为平均分换算成百分数。它们表示相似度，不表示有多少张表完全正确。

| 流程 | 样本数 | AccCon：整表内容完全正确 | GriTS Top：结构 | GriTS Con：内容 | GriTS Loc：位置 |
|---|---:|---:|---:|---:|---:|
| 论文参考：Canonical / DETR / All | 全测试集 | 81.38% | 98.45% | 98.46% | 97.81% |
| 本次官方评价条件基线 | 1000 | **82.10%（821 张）** | **98.20%** | **98.17%** | **97.38%** |
| 本次 TATR + PP-OCRv6 当前系统 | 1000 | **7.30%（73 张）** | **98.07%** | **93.73%** | **50.65%** |

论文参考来自 [PubTables-1M 表 4，第 8 页](https://arxiv.org/pdf/2110.00061#page=8)。本次基线与论文的差值依次为 +0.72、−0.25、−0.29、−0.43 个百分点。本次是 1000 张子集、微软 HF 发布权重和当前推理库的实验，接近的分数不能替代全测试集或重新训练实验。

两套流程各有 1000 份逐表 HTML、CSV、JSON。结构拓扑完全匹配（GriTS Top = 1）的表格分别为 825 张和 815 张；这与上表的平均结构相似度是不同统计量。

两套完整逐表结果均已归档到仓库：[下载官方基线与接入 OCR 的 1000 张结果包](full-results/README.md)。每套 ZIP 包含各 1000 份 HTML、CSV、JSON，以及逐表指标、固定名单、汇总、导出诊断和来源许可。

导出检查发现，官方基线有 25 张、当前系统有 27 张后处理结果包含重叠单元格，其中分别有 11 张和 16 张出现相同的左上角位置。HTML/CSV 只能投影成普通网格，同一位置的文字按现有导出规则保留最后一个单元格，不能完整表达这些歧义；JSON 保留全部原始单元格。指标由原始单元格计算，未根据导出的 HTML/CSV 重新评分或修正预测。案例名单见 [导出诊断](export-diagnostics.json)。这属于识别/后处理结果的问题，与“无程序运行失败”含义不同。

## 如何理解 OCR 版本的 7.30%

AccCon 按官方代码定义，单张表的 GriTS Con 必须恰好等于 1 才计为内容完全正确。保留原始空格、换行和符号，不做人为纠错。一个标点或单元格文本不同，就可能使整张表不再满足完全正确条件。7.30% 不能解释为“只有 7.30% 的表格能够使用”，93.73% 也不能称为“整表成功率”或单独的 OCR 字符准确率。

例如 `PMC1431516_table_0` 的两套结构分数均为 1，官方基线内容分数为 1，当前系统内容分数为 0.96852，但整表内容完全正确指标为 0。13 个单元格存在文本差异，包括 `4.15 [1.86–9.22]` 与 `4.15 [1.86-9.22]`、表头的标点与换行、占位短横线丢失。详见 [逐单元格示例](illustrative-case.json)。示例仅用于解释，未据此调整测试名单、阈值或模型。

GriTS Loc 的差距还涉及边界定义：官方后处理根据词框调整行列和单元格边界，当前系统先在空词信息上构造结构框，再填入 OCR 文字。两者形成的单元格边界不同，因此 50.65% 不能单独解释为 TATR 定位能力下降。后续应统一边界规则，并在相同预处理和后处理下单独检验 OCR 的影响。

## 抽样不确定性与耗时

样本来自 987 篇论文。按来源论文聚类进行 2000 次 bootstrap，种子 42，得到以下 95% 区间。区间反映本次随机子集的抽样不确定性，不覆盖模型版本或实验条件差异。

| 流程 | AccCon | GriTS Top | GriTS Con | GriTS Loc |
|---|---:|---:|---:|---:|
| 官方基线 | 79.74–84.41% | 97.73–98.60% | 97.70–98.58% | 96.78–97.91% |
| 当前 OCR 系统 | 5.79–8.99% | 97.60–98.46% | 93.08–94.32% | 49.73–51.55% |

本机 CPU 上，逐图结构推理、OCR 和后处理的累计平均耗时为：基线 1.27 秒，当前系统 3.59 秒，其中 OCR 平均 2.56 秒。不含模型加载、写盘及指标计算；阶段之间存在并行竞争，不能用这些数字直接比较论文硬件或推算整次实验的墙钟时间。

## 实验条件与复查

- 从官方 test 的 93,834 个 ID 中，排序后用 `random.Random(42).sample(..., 1000)` 无放回抽取；推理前固定名单，未按结果换图。
- 两套流程使用同一微软 HF 结构模型权重。基线使用官方最长边 1000 像素预处理、完整 softmax 类别筛选、官方词信息及后处理；当前系统使用原有 AutoImageProcessor、PP-OCRv6 small（放大 2 倍）和 `fuse()`。
- 使用相同官方 GT 单元格，以及固定版本、未修改的官方 GriTS / AccCon 函数。兼容层只将 NumPy 坐标标量转成 Python float，指标公式未替换。
- 两套流程同时存在预处理、词来源和后处理差异，因此这次对比不是仅改变 OCR 的消融实验。基线中的官方词信息属于论文评价条件，并非模型自行识别出的文字。
- 本实验验证预训练模型的推理与评估，不包含重新训练；输入是裁剪好的表格图片，不包含整页表格检测。

`manifest.json` 为公开镜像，省略了本机绝对路径，保留全部 ID、顺序和图片/XML 哈希；其中 `local_manifest_sha256` 指向本地原始名单。`predict-config.json`、`ocr-config.json`、`evaluation-config.json`、`words-provenance.json` 及 `ocr-metadata.json` 保留运行配置和来源。

`raw-stage-runner.py.txt` 保存原始推理启动时的脚本，供核查配置中的源码摘要。随后仅完善了词文件流式读取、失败恢复、缓存有效性、评分调度及报告说明；结构推理函数与当前入口的 AST 一致，OCR worker、融合及指标适配代码均未改变。新实验应使用仓库根目录的 `run_benchmark.py`。恢复同一阶段要求源码和配置匹配，不能把公开镜像当成带本机路径的运行目录。
